## 已知状态

- **悬浮指示器的固定像素尺寸在高 DPI 下会截断文字，且桩测试会给出假通过**（2026-08-12 实机暴露）：`recording_indicator.py` 的 `PANEL_W=450`/`TEXT_MAX_W=356` 是**物理像素**、不随 DPI 放大，而 Tk 字号是**磅值**、会随 DPI 放大。本机 200% 缩放（192 DPI）下 14pt 粗体「正在与“雾切响子”连续对话 12.3s」实测 552px，远超 356px，被 `_fit_text` 截成省略号；换句话说这个面板在 200% 下只有设计意图的一半宽。**降字号治不了**：11pt 时该标题仍要 432px，要塞进 356px 得降到约 9pt，比 10pt 的详情行还小。已改为按标题内容动态调宽（`_fit_panel_to_title`，可增可减，上限屏幕宽 90%），普通录音仍是 450px 不变。
  - 初版做成「只增不减」（照搬 `toast_base` 的流式增宽），实机反馈按空格加宽后再按回去右侧留一条白边。放开缩小的前提是**测量必须与动画帧解耦**：标题里有两处会每 100ms 变的东西，`等待识别结果.`/`..`/`...` 三帧实测 233/244/255px（差 22px，会让窗口每秒抖十次），以及录音秒数——后者不用管，实测 Microsoft YaHei UI 的数字等宽（各 23px），且同一次录音内单调递增。所以 `_compose_text(stable=True)` 把省略号固定成三个点专供测宽用。
  - **更隐蔽的是测试陷阱**：Python 进程默认不声明 DPI 感知，被系统虚拟成 96 DPI，`font.measure()` 量出来的宽度比实机小一半，于是「标题未被截断」的断言在测试里通过、在实机里失败。**任何涉及 Tk 文字度量的测试，必须在建 Tk 之前调 `ctypes.windll.shcore.SetProcessDpiAwareness(2)`**，否则结论不代表实机。scratchpad 的 `smoke_indicator.py` 已加这一步并断言 `winfo_fpixels('1i') > 96`。
  - 未做：整个面板按 DPI 等比放大（根因修法）。那会让悬浮框物理尺寸翻倍，用户未要求，2026-08-12 明确暂不做。（2026-08-12）

- LLM 角色偶发「空回复」：任务 `49be29b3-95c0-11f1-8481-581cf893a9d2`（2026-08-12 04:08，助理角色，第 4 轮对话，带选中文字的长技术问题）弹出白色 Toast 后 3 秒空着消失。**根因链已确认到客户端边界**：DeepSeek 的流跑了 4.88s 但一个 `response.output_text.delta` 都没有（终端结果行没有 `tokens/s` 后缀 ⇒ `generation_time == 0` ⇒ 从未收到分片），随后旧代码的 `polished_text or content` 把识别原文当成模型输出，控制台、`2026/08/12-助理.md` 全都伪装成一次成功回复；Toast 因最终文本 0 字，智能时长算出保底 3000ms 后自动关闭。**已排除**：ESC 中断、异常、联网搜索（无工具日志）、Toast 构造失败。
  - **服务端侧为什么空，仍未定**。最可能是 `max_tokens = 512` 映射成的 `max_output_tokens` 被不可见 token 耗尽——截断是「保留已生成部分」而非「丢弃」，本地也没有任何按长度裁剪的逻辑（`max_tokens` 只写进请求参数），所以正文一个字都没有，只能是额度在第一个可见 token 之前就被推理内容吃光。但**各家 API 对 max_tokens 是否计入思考 token 的口径并不一致**（OpenAI Responses `max_output_tokens`、Anthropic `max_tokens`、Ollama `num_predict` 都计入；DeepSeek 自家文档对 `deepseek-reasoner` 的说法是只限最终回答、不含 CoT），而本项目走的是 DeepSeek **Responses API + deepseek-v4-flash**，这条路径怎么算没有可靠依据。2026-08-12 已补诊断日志（约定 18），下次复现时用事件计数与 `usage.reasoning_tokens` 定论。
  - 关联未验证项：`extra_body={"thinking":{"type":"disabled"}}` 在 Responses API 上是否生效，从来没验证过（见本文件 2026-07-31 待验证条 ⑤）。

- 录音键（`ctrl_r`）的按下事件被吞掉、松开时前台程序却能收到一个抬起事件——**符合设计，不是 bug**（2026-07-28 用键盘测试网站观察确认）。原始 KEYDOWN/KEYUP 都被 `suppress_event()` 拦下，但 `event_handler._release_suppressed_modifier()` 会额外补发一个合成释放事件。理由见 `key_mapper.py` MODIFIER_KEYS 上方注释：低级钩子的抑制并非总是可靠（例如焦点在提权窗口上时钩子收得到却拦不住），一旦 KEYDOWN 漏过去而 KEYUP 被吞，修饰键会卡在按下状态，之后每次按键都变成组合键。这是刻意的不对称取舍——修饰键的释放是幂等的，多发无害；卡住的按下会持续污染后续输入。ESC 打断键因为不是修饰键、卡不住状态，反而采用严格配对、不做补发。
  - 边界：若把录音键换成 **Alt**，孤立的 Alt 抬起会被不少 Win32 程序当作激活菜单栏的信号，需要单独处理。
  - 可选优化（暂不做，2026-07-28 用户确认）：补发前先用 `GetAsyncKeyState` 判断系统是否真认为该键还按着，只在确实卡住时补发，可消掉正常路径上的多余事件。但抑制状态下该 API 的返回值是否可靠需实机验证。

- Toast 窗口构造异常会被 `ToastMessageManager._process_queue` 的 `except Exception` 吞掉，调用方只看到 `wait_for_window` 超时和「Toast 窗口创建失败」，看不出根因。2026-07-31 已给该 except 加 `exc_info=True`，但结构仍是「窗口构造失败 = 静默无弹窗」，改 `core/ui/toast_*.py` 后务必真的弹一次窗口验证，别只看有没有报错。（2026-07-31）

- Tk 几何字符串里负坐标必须写成 `+-100+50`：`wm geometry` 会把开头的 `+`/`-` 当作「从左/上边缘量」还是「从右/下边缘量」的标志位消费掉，符号后面的数字再单独按有符号数解析。所以 Python 的 `f"{x:+d}"` 对负数产出的 `-100+50` 会被理解成「窗口右边缘距屏幕右边缘 100px」，实测 1920 宽屏上 200px 宽的窗口会被摆到 x=1640。写位置一律用 `f"+{x}+{y}"`。（2026-07-31）

- Tk 的 `<Destroy>` 事件在 Toplevel 的**任意子 widget** 被销毁时也会触发绑定到该 Toplevel 上的回调（`toast_manager._process_queue` 里 `toast_window.window.bind('<Destroy>', ...)`），并非只在 Toplevel 本身销毁时触发。Markdown 转换（`_switch_to_markdown` 销毁 text_area 换 HTMLLabel）会误触发它，导致已 finish 的窗口被误从 `active_windows` 移除——窗口还在显示，但 `update_toast`/`close_toast`/`close_llm_windows` 都遍历不到它（这是 2026-08-08「新窗口顶不掉旧窗口」的根因）。2026-08-08 已在回调里校验 `str(e.widget) == str(w.window)`（Tkinter widget 对象非单例，不能用 `is` 比较，必须比较路径字符串）。改 toast 相关代码时注意别再用裸 `<Destroy>` 绑定做清理。（2026-08-08）

## 决策记录

- 连续对话定性为「免前缀粘滞路由」而不是「对话记忆」：记忆本来就有——`ContextManager` 按角色建实例、`enable_history=True` 的角色历史一直累积且没有按时间过期的清理，所以本功能的实际增量只有「免掉每句话开头念角色名」。据此进入时不清空历史、也不限制只有 `enable_history=True` 的角色能进（`翻译` 进去就是「连续翻译模式」，同样合理）。（2026-08-12）
- 路由用「每句话快照」而不是「结果到达时读全局状态」：按切换键在录音期间，命中哪个角色要等服务端回包，中间隔一整个往返。读全局状态会在两句重叠时错判，最难受的是退出方向——你以为已经说给角色的话，会因为手快按了退出而变成普通文本直接打进当前窗口。快照就是一个 `Dict[task_id, 快照]`，与 `state.audio_files` 同构，成本极低。（2026-08-12）
- 放弃「等结果期间禁止再次录音」这条更简单的方案：它确实能消掉竞态，但 `pending_task_id` 在断线时没人清（`_cleanup()` 只置空 websocket），服务端崩了就永久锁死录音，只能靠记得按 ESC 解锁——正是约定 12 当初拒绝在等待阶段拦截打断键的同一个理由；而且按下录音键没反应会让整句话凭空消失。它也并不省掉快照，只是把字典缩成单个标志。（2026-08-12）
- 连续对话中完全不做角色检测（而不是"命中别的角色就切过去"）：角色名是「翻译」「助理」这类日常词，`startswith` 匹配下对助理说「翻译一下这句话」会被静默劫持。换角色按一次空格退出即可，成本远低于误判。（2026-08-12）
- 「任何让这次录音作废的路径都回滚本次切换」优先于「退出是独立状态命令」：一条对称规则比分方向的例外好记，且与 ESC 既有语义（约定 12「本次输入彻底作废」）同源。代价是退出必须完成一次有效录音（静默长按 1 秒再松手即可，空识别结果不上屏）。（2026-08-12）
- 闲置超时用懒判断 + 静默退出，不开后台定时器也不弹 Toast：定时器要处理与钩子线程/事件循环的竞态，而判定结果只在按下录音键时才有意义；指示器每次录音都显示当前状态，足以自证。（2026-08-12）
- 切换键拒绝修饰键，不照录音键那样做补发兜底：补发合成释放事件对录音键是必要的恶（它必须能长按），切换键没有非用修饰键不可的理由，直接拒绝是最不容易出错的路。（2026-08-12）
- 指示器只用面板底色区分四态、圆点恒为蓝：底色已是足够强的状态信号，圆点跟着变等于同一信息重复两遍。浅黄表示「本次录音正在改变连续对话状态」（进入和退出都属此类，都可再按一次反悔），浅绿表示「已在连续对话中」，后者是防「忘了自己在连续对话里」的主要视觉信号。（2026-08-12）

- 工具调用回传用「出参列表」而不是把返回值扩成四元组、也不用 handler 实例属性：四元组要改三个输出模块里十余处 `return ("", 0, 0.0)` 的降级分支，漏一处就是运行时崩溃；实例属性会引入跨请求残留状态（识别结果虽是串行处理，但这类远距离作用日后极难排查）。代价是新增输出模式时必须记得转发 `used_tools`，漏了是静默无标签——已写进 PROJECT_INDEX 约定 16。（2026-07-31）
- 搜索发生后即使 LLM 报错降级或被 ESC 打断，标签照常显示「(搜索)」：它描述的是「本次请求做了什么」而非「结果来自哪里」，否则那次的耗时异常反而没有线索。（2026-07-31）

- 联网搜索用 DeepSeek Responses API 的服务端内置 `web_search`，不自己接第三方搜索 API、也不做本地关键词路由：内置工具不需要额外的搜索 API Key 和计费账户，检索在 DeepSeek 侧执行，客户端只多一条流式解析分支；「何时该搜」交给模型的工具调用判断，天然满足「简单问题不减速、时效问题才查」，而本地关键词/正则路由既会漏判（问「XX 发布了吗」不含时效词）又会误判（拖慢常识问答）。代价是该路径绑定 `deepseek-v4-flash`（当前唯一支持 Responses API 的模型），其他 provider 想联网需另写分支。（2026-07-31）
- 当前时间注入到用户消息而不是 system prompt：system 是服务端前缀缓存的命中前缀，逐分钟变化的时间戳会让每次请求都 cache miss（V4-Flash 命中/未命中价差 50 倍）。（2026-07-31）
- 联网搜索路径单独给 `request_timeout`，不改 `APIConfig.DEFAULT_TIMEOUTS`：全局 2s 超时是「网络有问题就快速失败」的刻意设计，检索请求只是首个分片前会静默数秒，属于个别角色的例外，用角色级字段按请求覆盖，不动全局。（2026-07-31）

- 角色 Toast 宽度配置彻底迁移为 `toast_min_width_px`/`toast_max_width_px` 与对应 ratio，不兼容旧 `toast_initial_width`：本项目为个人使用，不需要旧角色文件兼容层；像素值优先，非法时逐级回退比例和内置 320～800px，反向区间整体回退并警告，等宽区间允许用作固定宽度。（2026-07-28）
- 录音打断只改客户端，用「发 is_final 冲服务端缓冲 + 本地按 task_id 丢弃结果」实现：服务端跑在另一台机器上（地址见 `config_client.py` 的 `addr`），新增取消协议要跨机器维护并部署两份代码，收益只是省掉一次残余缓冲的推理，不成比例。断开重连虽然零推理浪费，但会把「取消一句话」和连接生命周期耦合，重连抖动会变成用户可见故障。（2026-07-28）
- 打断键与 `llm_stop_key` 拆成两个配置项：语义不同（作废输入 vs 停止输出并保留已输出内容），现在同为 esc 只是默认值巧合，复用会让改一个连带改另一个。（2026-07-28）
- 打断窗口截止到最终结果到达，不延伸到 LLM 生成阶段：那时文本很可能已经上屏到别的输入框，「丢弃」无法兑现；边界定为「结果到达前=作废，到达后=停止输出」。（2026-07-28）
- 打断键只在录音阶段拦截、等待结果阶段放行：录音状态由按键被按住这一物理事实兜底不会卡死，而等待状态依赖远程服务端回包，一旦不回，拦截会让该键全局失灵且极难排查。（2026-07-28）

- OpenMate 情绪标签使用稳定状态 ID，别名仅作提示词中的语义注解：ID 是 ASCII 稳定标识，规避 NFC 规范化和别名集合变动问题，OpenMate API 文档 §4.3 亦如此建议。（2026-07-16）
- OpenMate 接入采用无状态按需探测（每次 toast 请求前 GET /health，0.5s 超时），不维护长连接：OpenMate 可随时启停，无需重连逻辑；情绪状态列表缓存 5 分钟（失败缓存 1 分钟）。（2026-07-16）
- 不对 LLM 输出的情绪标签做本地校验：OpenMate 对无效状态回退默认立绘并剥离标签，本地增加跨分片流式校验层复杂度高且无用户可见收益。（2026-07-16）
- 本地定制的变更记录写本文件，不写 docs/CHANGELOG.md：后者是上游随版本发布的文件，混入本地条目会在升级覆盖时冲突。（2026-07-16）
