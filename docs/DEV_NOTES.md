  ④**陈图不再被误当成新图**：挂一张图 → 按 ESC 打断 → 再按 Ctrl+Alt+D 换一张（确认终端报的是新图的尺寸）→ 录音，确认模型看到的是新图。这是 2026-09-12 那次误判的原始场景。
  ⑤**回归**：普通小截图仍走 PNG（终端标的是 PNG，不是 JPEG），确认没有因为兜底分支拖慢正常路径。
  离线回归 `tools/test_vision.py` 已扩到 109 项（新增 17 项覆盖兜底决策、MIME 切换、原生 PNG 复用路径、编码异常不崩、`PendingImage.encoding` 默认值）。

## 已知状态

- **连按快捷键刷屏：合并闸门解决不了，靠剪贴板序号 + 提示去重**（2026-09-12 实机截图暴露，已修）：当天先加的「排队中最多留一个捕获」只能合并**一个捕获还排在队列里时**到来的按键，而剪贴板没变时时效检查 1ms 内就返回，人手速度的连按之间队列早就空了——实测 9 连按仍然刷了 9 行一字不差的「剪贴板自客户端启动以来未变动过」，另一批 10 连按刷了 10 行「已挂载图片」（同一张 401×169）。闸门防的是「大图解码几百毫秒期间连按导致任务堆积」，那是另一回事。**判据**：看两次按键的间隔与单次捕获耗时——前者远大于后者时闸门必然不生效。现在补了两道：剪贴板序号未变且图仍在待挂槽里就整个跳过（连解码和归档都不做），以及终端提示与上一条相同就不打。两道各管一头——前者管「同一张图重复挂载」，后者管「重复的失败提示」，缺一不可。

- **终端那条 `获取选中文字失败: (5, 'OpenClipboard', '拒绝访问。')` 与图片无关**（2026-09-12 实机反馈，已修）：它来自 `get_selected_text` 的**最后一步「还原剪贴板」**。原代码直接调 `pyclip.copy(original_clipboard)`，剪贴板被别的进程占着时抛 `ERROR_ACCESS_DENIED`，异常一路冒到外层 `except`，把**已经读到的选中文字一并丢掉**，并往终端刷一条 WARNING。日志里共 5 次，每次图片都正常上传了（如 03:40 那次传的是 1299×634），所以「附带图片时会失败」是这条告警造成的错觉。**但同一种占用确实也会挡住视觉侧**——`grab_clipboard_image` 的 `OpenClipboard` 失败此前只打 `logger.debug`（文件日志是 INFO 级，查都查不到），表现正是用户说的「再试一次就好」，典型触发场景是「截完图立刻按快捷键」，截图工具那时还占着剪贴板。已在两条路径统一加退避重试（5 次 × 20ms）。**重试必须只认「被占用」**：剪贴板里没有文本格式（典型是图片）同样抛异常，但那是稳定状态，无差别重试会让每一次带图对话固定多花 100ms——`get_selected_text` 每个请求都要走一遍，五个角色里四个开着它。

- **「按 Ctrl+Alt+D 没反应」的真实成因是体积上限，不是快捷键**（2026-09-12 实机误判，已修）：现象是连按快捷键都像没生效——下一次录音没有淡紫描边、模型也看不到图。日志里 03:09 到 03:19 之间有 **16 条**连续的 `图片编码后 xxxxKB 超过 1024KB 上限，已丢弃`，快捷键其实每次都正常触发、剪贴板也每次都读到了图。**判据**：先看日志里有没有这条超限记录，再怀疑钩子。当时另外两件事放大了误判：①这些提示全是 `logger.info`，而控制台固定在 WARNING，终端上成功和失败**长得一模一样**（都是什么都没有）；②`vision_manager` 把所有失败一律写成「剪贴板中没有可用图片」，日志里也看不出是体积问题。③失败时间点恰好和刚启用连续对话重合，于是被误归因到连续对话——实际两者无关，同一批失败横跨连续对话开着和关着两种状态。根因是照片/立绘/多图并排这类内容 PNG 几乎压不动（2000×1380 缩到 1920 宽后稳定 1.3~1.9MB），而上限当初是按界面类截图定的（4K 全屏实测约 350KB）。已改为 3MB + JPEG 兜底，并把每一种挂载结果都打到控制台（约定 21⑪）。

- **「读取选中文字」会把剪贴板里的图片清掉**（2026-09-04 实机日志发现并修复）：`llm_get_selection.get_selected_text` 是读—改—写——存原内容 → 模拟 Ctrl+C → 读 → `pyclip.copy(original)` 写回还原。而 pyclip 只认文本格式，剪贴板里是图片时 `safe_paste()` 抛异常、折叠成空串返回，那句「还原」就变成 `pyclip.copy("")`；Windows 写剪贴板必须先 `EmptyClipboard`，图片就此消失。日志现场是两条相隔 **0.104 秒**的 `剪贴板读取失败: Clipboard contents have no standard formats available`（正好是那句 `time.sleep(0.1)` 前后的两次读取）。这段代码一直如此，但以前剪贴板里几乎不会是图片；视觉输入一上线，**五个角色里有四个开着 `enable_read_selection`**，于是变成常态。最难受的顺序是「复制图片 → 忘了按 Ctrl+Alt+D 就直接说『助理 …』→ 剪贴板被清空 → 再按 Ctrl+Alt+D 只提示『没有可用图片』」，根本联想不到是上一句话干的。已新增 `clipboard.try_paste()`（读不到返回 None，与「本来就是空文本」区分开），`get_selected_text` 改为只在 `is not None` 时才写回；`safe_paste()` 保持原签名不变。同时把那条 WARNING 降为 DEBUG——剪贴板里是非文本属预期情况，而 `logger.py` 把控制台固定在 WARNING 级，带图对话时每句都会刷两行。**救不了的情形**：用户确实选中了文字时 Ctrl+C 本身就覆盖掉图片，那是模拟取选区的固有代价，除非连图片格式一并备份还原，不值得。（2026-09-04）

- **`estimate_tokens` 遇到多模态 content 会直接 TypeError**（2026-09-04 做视觉输入时复现并修复）：它是 `for c in text` 逐字符比较（`CN_CHAR_START <= c <= CN_CHAR_END`），而带图消息的 content 是 `[{'type':'text',...},{'type':'image_url',...}]` 这样的列表，迭代出来的是 dict，报 `'<=' not supported between instances of 'str' and 'dict'`。链路是 `llm_processor._stream_request` → `context_manager.add_message('user', messages[-1]['content'])` → `_trim_history()` → `estimate_tokens`，所以**凡 `enable_history=True` 的角色（助理、雾切响子、新岛真全是）第一次带图请求就会炸**。已改为列表按条目求和、图片按 DeepSeek 声明的 384 token/图 计（`ContextConstants.IMAGE_TOKENS`）——注意不能按 base64 字符数估，那会得出几十万 token 把裁剪逻辑整个冲垮。（2026-09-04）

- **进程 DPI 感知曾有三处互相覆盖的调用，实际生效的一直是 level 1**（2026-09-04 查清并统一）：`SetProcessDpiAwareness` 每进程只能成功一次，之后返回 E_ACCESSDENIED。`toast_base.py` 与 `dialogs.py` 在**模块导入时**声明 `1`（SYSTEM），`tray.py` 在函数体内声明 `2`（PER_MONITOR）；`app.py` 的导入链会先拉起 toast_base，所以 tray 那句从来没生效过，是被 `except Exception: pass` 吞掉的死代码。本机两块屏同为 192 DPI，1 与 2 表现一致，所以从没暴露——接一台 100% 缩放的显示器就会露馅。现统一到 `core/ui/dpi.py` 并**固定 level 1**（等同于此前实际生效的那条，行为零变化）；没有改成 2 是因为现有 Tk 布局全是硬编码物理像素、不响应 `WM_DPICHANGED`，换成 2 只会得到「清晰但尺寸错误」的窗口，不比 1 更正确。**顺带一个不一致仍然存在**：本文件要求 Tk 文字度量的冒烟测试声明 level 2，而生产是 1——本机同 DPI 所以既有结论仍然成立，换机器时要重新想。（2026-09-04）

- **本机显示器几何（做视觉输入时用 per-monitor v2 感知实测，非虚拟化数值）**：虚拟屏 `(0,0) 3840×4160`；主屏 DISPLAY1 `(0,0)-(3840,2160)`，副屏 DISPLAY5 `(485,2160)-(3685,4160)`，两块都是 192 DPI / 200%。**副屏在主屏正下方且左边缩进 485px**，所以虚拟矩形里有两条不属于任何显示器的竖带（`x∈[0,485)` 与 `x∈[3685,3840)`）。将来若真要自绘全屏遮罩（截图框选、屏幕标注之类），这两条空洞是必须处理的第一个边界。（2026-09-04）


- **服务端多候选有两个反直觉点，都是刻意设计不是 bug**（2026-08-12 随功能记下）：①**握手慢于探测超时的候选会被每一轮都跳过**，症状是「ping 得通却永远连不上」——排查入口只有调大 `addr_probe_timeout`（公网/域名档）或 `addr_probe_timeout_lan`（内网档）；注意分档按配置里写的字符串判定，域名即使解析到内网也走保守档。②**一次瞬时握手成功就会锁定**，哪怕服务端下一秒崩溃，此后也只等它恢复、不改投其他候选；这是「断开也不切换」需求的直接推论。另：IPv6 字面量未支持（`'::1'`、`'[::1]:6000'` 都会拼出畸形 URL），会在日志与启动提示里原样暴露，不静默。（2026-08-12）

  - 初版做成「只增不减」（照搬 `toast_base` 的流式增宽），实机反馈按空格加宽后再按回去右侧留一条白边。放开缩小的前提是**测量必须与动画帧解耦**：标题里有两处会每 100ms 变的东西，`等待识别结果.`/`..`/`...` 三帧实测 233/244/255px（差 22px，会让窗口每秒抖十次），以及录音秒数——后者不用管，实测 Microsoft YaHei UI 的数字等宽（各 23px），且同一次录音内单调递增。所以 `_compose_text(stable=True)` 把省略号固定成三个点专供测宽用。

- 图片寿命定为严格「下一条」，不设闲置超时：超时静默失效时用户看不到通知、无法确定下一句会不会带图；而弹通知又太吵。严格语义最清晰——下一次录音一旦有效落地，图必然消失。**命中了角色但该角色 `enable_vision=False` 也照样丢弃**，一条规则不留例外，否则等于把「图什么时候真的消失」的不确定性又请回来。（2026-09-04）

- 唯一的可见信号是录音悬浮框最外圈描边变色，不弹任何 Toast：信号出现在唯一还来得及补救的时刻（录音刚开始、话还没说），且零打断。原本提议的「按下快捷键时弹回执」被否——那是事前提示，而挂载失败真正需要被发现的时刻是「即将说话」而非「刚按完键」。占用描边通道不与连续对话冲突：约定 19⑧ 说的是「四态只用面板底色区分」，描边一直只是跟随底色的配色。（2026-09-04）
- 历史里只保留最近一张图，更早的降级成 `［图片］`：截图提问天然多轮（「这什么报错」→「那第三行呢」），模型必须还能看见最近那张；但全留着就要每轮重传所有图，而历史没有按时间过期的清理，图会一直占内存直到被 token 压力挤出去。（2026-09-04）
- 图片加时效检查（`vision_clipboard_max_age`，默认 60s）：淡紫边框只回答「这次带了图吗」，不回答「带的是哪张」，所以「本以为附上刚截的图、实际附的是一小时前那张」这种误配它看不出来——正是时效检查补的那一格。剪贴板不带时间戳，只能自己轮询序号记录变更时刻。**没有做事件驱动的 `AddClipboardFormatListener`**：那要建 message-only 窗口 + 消息泵线程，而轮询实测成本是 0.33 毫秒 CPU/小时（周期 5s、单次 0.455µs），已在噪声底下——比录音指示器录音期间的 100ms tick 和热词 watchdog 都低几个数量级，为它引入一套 Win32 窗口管理不划算。**启动后剪贴板没变过时按「过期」而不是「新鲜」**：规则既然是「必须是近 N 秒内写入的」，证不出来就不算，否则重启客户端会让放了一天的旧图凭空变新；代价是重启后需要重新复制一次，属低频摩擦。（2026-09-04）
- ~~PNG 超 1MB 直接丢弃，不做 JPEG 兜底~~（2026-09-04 的取舍，**2026-09-12 推翻**）：原理由是「JPEG 重编码会额外引入一次编码延迟」，并接受「照片会经常被拒」。实机否掉了这个取舍的前提——主线用例并不只是界面截图：立绘比对、多图并排这类内容 PNG 压不动，一晚上连续 16 次挂载全被挡下，而用户完全看不出发生了什么。新方案是上限提到 3MB，**且只在缩放后 PNG 仍然超限时才转 JPEG**（质量 85），没超限的照旧原样发 PNG——延迟顾虑因此只落在罕见路径上，而那条路径的替代品是「彻底用不了」。没有同时调小 `MAX_EDGE_PX`（1920 → 1280）：那会无差别牺牲所有图的清晰度去迁就少数大图，而兜底只在需要时才付代价。（2026-09-12）

- 服务端多候选「首次连接成功才锁定」而不是「启动时探测一轮定终身」：客户端常随开机自启，那一刻服务端往往还没起来，按启动时刻定终身会锁死在不可达地址上，只能重启客户端解套。代价是「锁定」发生的时刻不确定，但用户可见行为是一致的——连上哪个，绿色的「已连接服务端」行就是哪个。（2026-08-12）
- 探测超时按内网/公网分档，且不复用 `ipaddress.is_private`：短超时的真实风险是「可达的机器被静默跳过，而且每轮都跳过」，内网握手在十几毫秒量级、2s 有两个数量级余量，域名与公网则无从判断，只能给一档保守值。`is_private` 涵盖 169.254/16、198.18/15、240/4 等保留段，口径比 RFC1918 宽，会把链路本地地址误划进短档。（2026-08-12）

- 锁定后不提供托盘「重新选择服务端」，换机一律重启客户端：解锁要处理「解锁瞬间正在录音/正在等结果」以及跨线程强制断开当前连接，是一片新的竞态面；而换服务器是低频事件，重启的代价只是丢掉 LLM 各角色的对话历史。（2026-08-12）
- 连续对话定性为「免前缀粘滞路由」而不是「对话记忆」：记忆本来就有——`ContextManager` 按角色建实例、`enable_history=True` 的角色历史一直累积且没有按时间过期的清理，所以本功能的实际增量只有「免掉每句话开头念角色名」。据此进入时不清空历史、也不限制只有 `enable_history=True` 的角色能进（`翻译` 进去就是「连续翻译模式」，同样合理）。（2026-08-12）

- 切换键拒绝修饰键，不照录音键那样做补发兜底：补发合成释放事件对录音键是必要的恶（它必须能长按），切换键没有非用修饰键不可的理由，直接拒绝是最不容易出错的路。（2026-08-12）
- 指示器只用面板底色区分四态、圆点恒为蓝：底色已是足够强的状态信号，圆点跟着变等于同一信息重复两遍。浅黄表示「本次录音正在改变连续对话状态」（进入和退出都属此类，都可再按一次反悔），浅绿表示「已在连续对话中」，后者是防「忘了自己在连续对话里」的主要视觉信号。（2026-08-12）

- 搜索发生后即使 LLM 报错降级或被 ESC 打断，标签照常显示「(搜索)」：它描述的是「本次请求做了什么」而非「结果来自哪里」，否则那次的耗时异常反而没有线索。（2026-07-31）

- 联网搜索用 DeepSeek Responses API 的服务端内置 `web_search`，不自己接第三方搜索 API、也不做本地关键词路由：内置工具不需要额外的搜索 API Key 和计费账户，检索在 DeepSeek 侧执行，客户端只多一条流式解析分支；「何时该搜」交给模型的工具调用判断，天然满足「简单问题不减速、时效问题才查」，而本地关键词/正则路由既会漏判（问「XX 发布了吗」不含时效词）又会误判（拖慢常识问答）。代价是该路径绑定 `deepseek-v4-flash`（当前唯一支持 Responses API 的模型），其他 provider 想联网需另写分支。（2026-07-31）
- 当前时间注入到用户消息而不是 system prompt：system 是服务端前缀缓存的命中前缀，逐分钟变化的时间戳会让每次请求都 cache miss（V4-Flash 命中/未命中价差 50 倍）。（2026-07-31）
- 联网搜索路径单独给 `request_timeout`，不改 `APIConfig.DEFAULT_TIMEOUTS`：全局 2s 超时是「网络有问题就快速失败」的刻意设计，检索请求只是首个分片前会静默数秒，属于个别角色的例外，用角色级字段按请求覆盖，不动全局。（2026-07-31）

- 角色 Toast 宽度配置彻底迁移为 `toast_min_width_px`/`toast_max_width_px` 与对应 ratio，不兼容旧 `toast_initial_width`：本项目为个人使用，不需要旧角色文件兼容层；像素值优先，非法时逐级回退比例和内置 320～800px，反向区间整体回退并警告，等宽区间允许用作固定宽度。（2026-07-28）
- 录音打断只改客户端，用「发 is_final 冲服务端缓冲 + 本地按 task_id 丢弃结果」实现：服务端跑在另一台机器上（地址见 `config_client.py` 的 `addr`），新增取消协议要跨机器维护并部署两份代码，收益只是省掉一次残余缓冲的推理，不成比例。断开重连虽然零推理浪费，但会把「取消一句话」和连接生命周期耦合，重连抖动会变成用户可见故障。（2026-07-28）
- 打断键与 `llm_stop_key` 拆成两个配置项：语义不同（作废输入 vs 停止输出并保留已输出内容），现在同为 esc 只是默认值巧合，复用会让改一个连带改另一个。（2026-07-28）
- 打断窗口截止到最终结果到达，不延伸到 LLM 生成阶段：那时文本很可能已经上屏到别的输入框，「丢弃」无法兑现；边界定为「结果到达前=作废，到达后=停止输出」。（2026-07-28）
- 打断键只在录音阶段拦截、等待结果阶段放行：录音状态由按键被按住这一物理事实兜底不会卡死，而等待状态依赖远程服务端回包，一旦不回，拦截会让该键全局失灵且极难排查。（2026-07-28）

- OpenMate 情绪标签使用稳定状态 ID，别名仅作提示词中的语义注解：ID 是 ASCII 稳定标识，规避 NFC 规范化和别名集合变动问题，OpenMate API 文档 §4.3 亦如此建议。（2026-07-16）
- OpenMate 接入采用无状态按需探测（每次 toast 请求前 GET /health，0.5s 超时），不维护长连接：OpenMate 可随时启停，无需重连逻辑；情绪状态列表缓存 5 分钟（失败缓存 1 分钟）。（2026-07-16）
- 不对 LLM 输出的情绪标签做本地校验：OpenMate 对无效状态回退默认立绘并剥离标签，本地增加跨分片流式校验层复杂度高且无用户可见收益。（2026-07-16）
- 本地定制的变更记录写本文件，不写 docs/CHANGELOG.md：后者是上游随版本发布的文件，混入本地条目会在升级覆盖时冲突。（2026-07-16）
